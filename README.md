# Octoterm

English | [中文](README-cnzh.md)

A tiny, memory-frugal terminal server: a daemon hosts pty sessions that survive
disconnects, and clients attach over a WebSocket binary protocol with seamless
resume. It is not a tmux wrapper — it extracts the kernel of what tmux does
(process + IO + screen-state hosting) and gives window management back to the
client.

## Why

This project is inspired by tmux: a hosted, always-on console is something you
end up needing constantly. Jupyter's built-in terminal already nails the
experience — open a browser, get a live shell that survives the tab — but it is
deeply bound to Jupyter itself. What was missing is an **extremely lightweight,
memory-frugal standalone terminal server**.

That is octoterm's entire positioning. And unlike tmux, its GUI is not a pure
in-terminal UI: sessions are exposed through a client-neutral wire protocol, so
you can operate them from a browser or the native Android client.

## Philosophy

A memory-frugal Swiss Army knife — and it stays that way:

- **Small**: single static binary, one process, minimal resident footprint.
- **Restrained**: the minimum feature set that meets the need, done well.
- **Not all-in-one**: window management belongs to clients; anything a hosted
  shell can already do (editors, file tools) will not be rebuilt into the
  server.

## Quick start

```sh
# Requires Node/npm: the server's build.rs builds clients/web automatically
# (set OCTOTERM_SKIP_WEB_BUILD=1 to skip it)
cargo run -p octoterm-server
# The startup log prints a ready-to-open URL (Jupyter-style; a fresh random
# token is generated on every start):
#     http://127.0.0.1:7683/#token=<random token>
```

To pin a fixed token (so open pages survive server restarts), pass
`--token <value>`, or put `token = "<value>"` in a config file. The config file
is never auto-generated by the server; create it yourself at
`~/Library/Application Support/octoterm/config.toml` (Linux:
`~/.config/octoterm/config.toml`), or point at one with `--config <path>`. All
fields are optional:

```toml
listen = "127.0.0.1:7683"
token = "my-fixed-token"
# When several clients attach the same session, one pty has one size, so their
# requested sizes are merged: "smallest" (default, nobody sees a truncated
# screen), "largest", or "latest" (follow the most recent client).
window_size = "smallest"

# Extra entries for the "new session" menu. Optional — the menu already lists
# your default shell plus anything it finds in iTerm2 / Windows Terminal.
[[launcher]]
name = "prod ssh"
command = ["ssh", "prod01"]   # argv, not a command line: no quoting rules to guess
cwd = "~/work"                # optional
```

### The "new session" menu

Clicking **+** opens a menu instead of a prompt. Its entries come from
*providers* on the server, so there is nothing to configure for the common case:

| provider | where it looks |
| --- | --- |
| built-in | `$SHELL` (unix) / `powershell.exe`, `%ComSpec%` (Windows) |
| config | `[[launcher]]` in the config file above |
| iTerm2 | `com.googlecode.iterm2.plist` + `DynamicProfiles/` (macOS) |
| Windows Terminal | `settings.json` (packaged, preview and portable installs) |

Third-party configs are **read, never written**. Only profiles that differ in
what they run — a custom command or a custom working directory — are listed;
colour-scheme-only profiles are noise here. A provider that fails (missing,
corrupt, unreadable) is skipped with a log line; the menu still works.

Adding a source is one `LauncherProvider` impl in `crates/server/src/launcher/`.

By default the server listens on 127.0.0.1 only. To reach it from other
devices, override on the command line (takes precedence over the config file):

```sh
cargo run -p octoterm-server -- --host 0.0.0.0 --port 9000
```

With `--host 0.0.0.0`, startup logs list token-bearing URLs for localhost and
each IPv4 address on an active network interface, including LAN and VPN addresses.

When exposing it beyond localhost, bring your own network-layer security
(Tailscale / reverse proxy + TLS).

On each startup, the server checks the latest stable GitHub Release in the background.
If a newer version is available, it prints the version and Release page URL to the
console. Offline or failed checks do not interrupt startup.

## Desktop app (Windows / macOS)

`octoterm-desktop` runs the same server embedded in a tray-resident process,
with a small native settings window. It is not a terminal client — terminals
still live in the browser.

```sh
cargo run -p octoterm-desktop
```

The desktop app also checks for a newer stable Release at startup. A native dialog
offers “Update now” (立刻更新) to open the Release page in your default browser, or
“Cancel” (取消) to keep working. Updates are never downloaded or installed automatically.

Changing the listen address or token from the settings window only rebuilds
the HTTP layer: **your running sessions are not affected**. But a page you
already have open does not get migrated — its WebSocket was never closed, so
it keeps talking to the old address until you close it yourself; only new
connections pick up the new one. Quitting the app does terminate every
session, so it asks for confirmation first if any are running.

**The chat view, and what it exposes**: when a hosted session is running Claude
Code, you can open it as a structured message stream instead of a VT screen. It
reads the agent's own transcript — **read-only, never cached, never written** —
and is gated by `agents.transcript_enabled` (on by default; set it to `false` under `[agents]` to turn it off).

That is a separate switch from installing hooks on purpose: hooks let octoterm
see *what it is doing*, this one lets it see *what was said* — code, paths,
commands, the model's reasoning. An order of magnitude more exposure, and not
something the first switch should quietly imply. **Read it together with the
next paragraph**: the desktop app listens on every interface by default, and
both switches are on by default, so anyone on your LAN holding the token can
read your whole conversation — turn it off on untrusted networks, or listen on
127.0.0.1 instead.

**Hook self-check and cleanup**: on every start (and whenever the desktop app
restarts the server on a new port) octoterm checks that installed hooks match
the running server — port, events, binary path — and prints a warning when they
don't. It only reports; fixing is still the "Reinstall" button under Settings →
AI integration. For leftovers, use "Purge" on the same page or run
`octoterm-server purge-hooks`: it removes **every** hook octoterm ever wrote
into an agent's config (any port, any event), leaves your own hooks alone, and
backs the file up first.

**It listens on `0.0.0.0:7683` by default — unlike `octoterm-server`.** Reaching
your machine from a phone or tablet is the whole point of the desktop app, and a
loopback-only default makes it unusable out of the box. Two hard boundaries make
that defensible: an empty token cannot reach the listener (enforced in release
builds too), and `/hook/*` accepts loopback peers only, whatever the main listen
address is. The residual risk is real — anyone on your LAN who has the token has
your terminal — so on an untrusted network set it back to `127.0.0.1` in the
settings window, or put your own network-layer security in front of it.

Linux is not supported.

## Android client

`clients/android` is a native Kotlin + Jetpack Compose client with connection
management, server launchers, multiple sessions, scrollback and text selection.
Connected servers are managed at application level: returning to the session or
server list keeps the server WebSockets open. Leaving a terminal, switching to
chat, or backgrounding the app detaches its terminal viewport so other clients
regain their screen size. Opening the terminal again attaches it automatically.
The server list shows each connection's state and offers reconnect/disconnect.
Background connections are enabled by default and use a foreground service with
an ongoing notification; its action disconnects all servers. Settings can limit
connections to the foreground instead. Cloud push remains a separate fallback
when a server is unreachable or Android stops the process.

The UI and terminal follow the system using `2026 Light` / `2026 Dark`. The
terminal viewport shrinks above the soft keyboard, and shortcut keys scroll
horizontally in two rows by default. The home screen settings icon combines
language, appearance and the one/two-row shortcut preference. Keys are 35dp square.
When the server identifies the active terminal's agent, the shortcut bar switches
to an agent layout with Page Up, Page Down and multiline keys first. Under
**Settings → Agent shortcut layouts → Configure**, each agent can independently
use Ctrl+J, Shift+Enter or both, reorder other priority keys, or use the regular
terminal layout. Preferences are saved locally.

For Windows servers, the keyboard adapter preserves key identity and modifiers
for Shift+Enter, Ctrl+J, Alt+arrows and other combinations. The shortcut bar
includes Esc, Ctrl+C, arrows, Home, End and PgUp/PgDn.

Build with JDK 17 and Android SDK 36, or open `clients/android` in Android Studio:

```sh
cd clients/android
./gradlew :app:assembleDebug :app:testDebugUnitTest
adb install -r app/build/outputs/apk/debug/app-debug.apk
```

Use `gradlew.bat` on Windows. After installation, add the server address and
token, or import the server access URL from the clipboard.

## Agent session history

Use the history button in the web sidebar or **Agent session history** on the
Android server screen to browse host-side Claude Code, Codex, pi, Grok and
Antigravity CLI records, including conversations started outside Octoterm.
Filter by agent or search titles, working directories and session IDs, and
preview recent messages.

An associated live Octoterm terminal opens directly. Otherwise, resuming creates
a new Octoterm terminal in the original directory. The corresponding CLI must
be on the server PATH, the directory must exist, and the record must contain
the required metadata. pi resumes using its original session file. Concurrent
resume requests share the same terminal.

History uses the server bearer token and `[agents].transcript_enabled`. Startup
asynchronously indexes at most 1000 distinct recent sessions. Clients load 50
metadata entries per page and display the limit at the end of the list. Transcript
bodies load only for previews. Refresh rebuilds the index in the background while
reads use the previous snapshot. Discovery and reads remain bounded; the UI
reports incomplete scans and unreadable records. This version reads default
agent stores for the server user, excluding WSL, other users and custom roots.

## Octoterm Cloud (optional)

Signing in to Octoterm Cloud lets agent "waiting for you" events reach your phone as push notifications when push is configured in the Android build. Everything works without signing in.

- Cloud never relays terminal data and never sees this machine's access token; a push carries only the session number, agent name and tool name.
- The sign-in state lives in `cloud.json` in the config directory, with owner-only permissions (0600) on Unix.
- The desktop app and a standalone `octoterm-server` running on the same machine share this file, so signing in (or out) from either one is reflected in both.

```bash
octoterm-server cloud register        # sign up and sign in (email code)
octoterm-server cloud login
octoterm-server cloud status
octoterm-server cloud logout
octoterm-server cloud reset-password
octoterm-server cloud delete-account  # permanently delete the account and all its data
```

Set a default Cloud address in `config.toml`:

```toml
[cloud]
url = "https://cloud.example.com"
```

Desktop users select a relay region in the "Cloud account" section of Settings and click
"Sign in through browser". Sign-in, registration and password recovery happen in the browser;
Desktop receives a loopback callback and saves the sign-in state automatically.

| Relay region | Address |
|---|---|
| Mainland China (default) | `https://octoterm.signal.top/` |
| North America (not deployed yet) | `https://octoterm.eclosion.ai/` |
| Other global regions (not deployed yet) | `https://global.octoterm.eclosion.ai/` |

Cloud must run a version with `/auth/desktop` and `/v1/auth/desktop/*` support.
Android uses the same three relay presets and a browser sign-in flow, with registration
and password recovery on the web page. The browser returns to the app, which saves a
device credential and registers for push notifications. Android requires the Cloud
`/auth/mobile` and `/v1/auth/mobile/*` endpoints. The account icon turns the theme's
accent color with a small check when signed in, and shows a small cross when signed out.
The account page reports push registration status and offers a retry. Cloud selects
Aliyun or FCM through its deployment configuration; Android reads `/v1/push-config`
and registers with that provider. Put the downloaded Aliyun client configuration at
`clients/android/app/aliyun-emas-services.json` (ignored by Git). Its app credentials
are separate from the server-only Alibaba Cloud AccessKey. Aliyun does not require
Google Play services; FCM requires Google Play services and network access to Google.
Both routes require notification permission. Aliyun's proprietary channel requires
the app process to be runnable; vendor channels need additional SDKs and credentials
for timely delivery when the process has been killed.
Updated Desktop/server builds also send a notification when a Stop hook completes a turn.
Sign-in can be cancelled and expires after 10 minutes. The callback listens only on
`127.0.0.1` using a temporary port.

## Architecture

Wire protocol: [`docs/protocol.md`](docs/protocol.md) — the normative spec, and
the checklist any protocol change has to pass. Background and rationale:
`docs/superpowers/specs/2026-08-16-octoterm-design.md`.

- `crates/protocol` — frame and message definitions (single source of truth)
- `crates/server` — the daemon: pty hosting, server-side grid, WebSocket
- `crates/client-core` — reusable logic for Rust clients
- `crates/desktop` — tray-resident GUI with the server embedded (Windows / macOS)
- `clients/web` — reference client (TypeScript + xterm.js)
- `clients/android` — native Android terminal client (Kotlin + Jetpack Compose)

## Roadmap

octoterm is currently an **experimental demo**, with browser and native Android
clients available.

1. **More terminal capability, more clients.** Deepen core terminal features,
   continue improving Android, and bring the same protocol to iOS and other platforms.
2. **Agent integration.** A hosted session lets you take over an agent's
   prompts, answer its choices, and check its status from any device.
   **Claude Code works today** (hook install, live session state, remote
   approval, chat view). Codex is supported too (state, approval, chat view;
   its hooks must be reviewed once with `/hooks`). **pi** is supported through a
   generated extension at `~/.pi/agent/extensions/octoterm.ts` (state and chat
   view; pi has no approval prompts, so there is nothing to approve remotely).
   **Grok** (xAI's `grok`) is supported through `~/.grok/hooks/octoterm.json`
   (state and chat view; it has no approval event either). **Antigravity CLI**
   (Google's `agy`) is supported through an `octoterm` entry in the shared
   `~/.gemini/config/hooks.json` (state and chat view; its own permission
   prompts are left alone).
3. **No file manager.** File management is very unlikely to ever be added —
   that's what the shell in your session is for.

## Known limitations

Resync restores content, cursor and common modes (application cursor keys,
bracketed paste, mouse reporting), but not the alt screen or scroll regions
(DECSTBM). After a rough-network reconnect, full-screen apps may need a Ctrl-L
or an app-level redraw.
